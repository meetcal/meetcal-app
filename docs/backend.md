# Convex backend

The backend lives in `convex/`. Deployments:

| | Deployment | Used by |
|---|---|---|
| Dev | `utmost-retriever-826` | `npx convex dev`, `development*` EAS builds |
| Prod | `disciplined-hare-790` | `preview` and `production*` EAS builds, iOS App Intents |

## How data changes

Every write to competition data goes through the internal mutations in `convex/ingest.ts`. The scrapers (`convex/scrapers/`, scheduled by `convex/cronJobs.ts`) and `scripts/usamw-results.ts` all use them. Each ingest write:

1. writes the rows;
2. rewrites the touched athletes' **history** (`athlete_history`) and **summary** (`athlete_summary`) documents in the same transaction, so those can never lag behind `lifting_results`;
3. leaves **hints** naming what changed (a meet, a ranking class, an athlete, a reference table), then schedules a refresh.

Freshness is tracked per view: while a hint a view depends on is pending, that view is not served as fresh, and every other view is. A few seconds later `views:refresh` uses the hints to rebuild only what those rows feed:

- the materialized views (meet packages, rankings, reference tables, clubs, WSO records);
- the search **directory** and its two-letter **shards**, adding names that gained results and removing names left with none.

So new athletes, new results, deletions and new meets update everything on their own. Nothing needs to be run by hand.

The refresh deletes each group's hints as soon as its builds succeed. A build that throws (a malformed row, a meet past a read limit) is logged and keeps its hints, so only the views it names stay stale and the next refresh retries it; the hourly `views-refresh` job fails, and so alerts, while one does. A refresh stops after three minutes and queues another for what is left. It reads at most 3,500 hints; past that it handles those and queues another refresh at once. Only more than 2,000 hints of the kinds that each cost a view build (meets, ranking classes, tables) start a full rebuild instead. A meet's year-best and stats views look up their own roster's athlete hints one key at a time (rosters up to 1,500 athletes), so a write about other athletes leaves them fresh and their cached answers valid. While only a package's year bests are stale, `meets:packageForMeet` serves the built static part and computes just the bests. Athlete hints carry the earliest result date they changed, so a meet's club stats (which depend only on earlier results) are rebuilt only when that date comes before the meet; its year-best timelines always are. The meets a refresh checks rosters of come from a maintained meet index (`index|meets`), not a scan of the tables.

A combined national event is one Sport80 entries event (the meet, with its start list) and several results events, each stored under its own title. Link those titles to the meet with `npx convex run ingest:setMeetResultTitles '{"meet":"…","titles":["…","…"]}'` (it answers each title's result count, and `"titles":[]` unlinks). The meet's results, package, stats and club stats then read every linked title, and a write under a linked title marks the meet's views stale too.

What the writers match on:

- A result is identified within its event by meet, folded name (`normalizeName`: Unicode NFC, whitespace collapsed, lowercased) and age category (`ingest.resultKey`). The upsert, `deleteLiftingResults` and the Sport80 prune all use that key, and the upsert deletes a second stored copy of a row it updates. The pre-Convex import stored some meets' editions under one event id, so the key can also name another year's real result: the upsert matches only stored rows dated within 180 days of the incoming row (`ingest.SAME_EDITION_DAYS`; a copy stored under a wrong date stays a duplicate rather than risk deleting another edition's result), and the prune judges only rows dated within that window of the payload's (`ingest.sameEditionRows`, `sameEditionDates`). `deleteLiftingResults` deletes the key in every year.
- `npx convex run migrations:dedupeLiftingResults` deletes rows stored twice under one key: one edition (dated within 180 days), same body weight, attempts, total, federation and adaptive flag, keeping the newest and its pre-Convex serial. Rows under a key that differ (another edition, or two sets of values) are logged as `dedupeLiftingResults: left …` for a person, never deleted. Run it with `'{"dryRun":true}'` first and read the logs. It deletes through the ingest path, so histories, summaries, views and search follow on their own.
- A meet is identified by its name, everywhere (rosters, results, schedules, views, saved sessions), and a stored name never changes. The Sport80 meet sync (`meet-sync`) reads the widget's whole listing of upcoming events once and syncs the WSO, national and Virus series meets in it (by title), plus every meet it has stored under that event's id (`meets.sourceId`), whatever the title now. It matches a meet on the Sport80 event id first, then on name and federation (the USA Masters sync, on name and federation), and a meet matched by name takes the event's id. So a meet Sport80 retitles stays one meet under its stored name, with the new title in `sourceName`, and the run fails once naming it; the `entries` job finds a target's meet by the event id in its URL (else by the list's title) and writes under the stored name, and fails a target whose list is no stored meet. A meet stored before it had an id, then retitled, is tied to its event by hand: `npx convex run ingest:setMeetSourceId '{"name":"…","sourceId":"<event id>"}'`. The meet sync also fails, naming the meet, while a stored upcoming meet's event is missing from the listing (cancelled or deleted on Sport80). A new meet whose name another meet already has (usually another federation's) is stored as `<name> (<federation>)` (or `<name> (<federation> 2)` and on if a meet holds that too), with the source's name in `sourceName`, never over the other meet, and its sync (`meet-sync`, `usamw-events`) fails once so the alert names it: results and entries sent under the plain name still attach to the other meet until a person renames one. `npx convex run migrations:duplicateMeetNames` lists names held by more than one meet row (readers use the oldest).
- A meet's status follows its dates on its own calendar: `upcoming`, `ongoing` from its first day, `completed` after its last. The meet syncs set it on every write, and the hourly `complete-ended-meets` job (`ingest.updateMeetStatuses`) moves it as the days pass. `completed` is final (`nextMeetStatus`): neither the syncs nor the job move a completed meet back to `upcoming` or `ongoing`, so a meet marked completed by hand before its dates stays completed. A meet auto-completed from a wrong past date stays completed after the source fixes the date. Set a status by hand with `npx convex run ingest:setMeetStatus '{"name":"…","status":"upcoming"}'` (or `"completed"` to finish a meet before its dates), not in the dashboard: the meet's package carries its status, and only the mutation refreshes it. A meet with a blank or unreadable zone is read on the calendar of UTC-12, the last place a day begins and ends, so it never turns `ongoing` or `completed` before its first day has begun, or its last has ended, everywhere.
- Genders are stored as `Men` / `Women` (`normalizeGender`). The athlete answers (start lists, rosters, club and WSO registrations) give `Male` / `Female`, the spelling the apps filter on.

Clubs are stored as each registrant typed them. A club is every spelling that folds to one key (`lib/clubs.ts`, `clubKey`: case, spaces and punctuation ignored, so `ONG weightlifting`, `Ong Weightlifting` and `RoseCity` / `Rose City.` are one club each); the club list shows one label per club, the builder also stores every spelling of each (`ref|club_spellings`), and `clubAthletes`, `clubMeets` and `clubMeetStats` read every spelling of the club they are given. `clubMeets` (the app's club meets list, the site's Club Dashboard Meet picker) answers a club's distinct meets, newest first, with each meet's date, status and whether it has results: one `by_club_and_meet` seek per meet, not one read per registration, at most `MAX_CLUB_MEETS` meets and a fixed index-range budget, with `truncated` set when it stops early. Abbreviations (`FXT BB` for `FXT Barbell`) are not folded. The club-list builder reads at most 100 distinct club names per query and publishes the completed list in one mutation. A roster write during the scan renews the club hint, so the view stays stale for another refresh rather than marking mixed data fresh.

National ranking builders and their live parity checks read at most 1,000 results per query, merging each athlete's best total across pages. Builders publish only the complete ranking, with the same freshness guarantee. An athlete is one ranking row under any spelling of their name (folded, as `normalizeName` folds it), shown under the spelling of their best result. A result whose numbers cannot be real is not ranked (`lib/plausible.ts`: a total that is not snatch + clean & jerk, a made attempt one and a half times the lifter's other attempts in the lift and 20 kg heavier, as a `633` typed for `63` is, or a lift or total over the world records). The rankings are views, so after a deploy that changes this rule, rebuild them (`views:rebuildAll`).

`scripts/usamw-results.ts` checks every row it parses the same way, and also refuses a body weight outside 20-250 kg and attempts that go down within a lift: it prints each failing row with its PDF line and writes nothing unless `--skip-invalid` (which writes the rows that pass). It refuses a PDF in which no attempt reads as a miss while most totals disagree with the bests (misses marked other than in red) outright.

Some events' results were stored by an earlier loader under each lifter's birth date, or one day per lifter. `npx convex run migrations:resultDateProblems` lists the events whose results carry about one date per lifter; `migrations:redateEventResults '{"eventId":"…","meet":"…","date":"YYYY-MM-DD"}'` shows what it would change, and with `"dryRun":false` gives those rows the event's date through the write path (200 a call; rerun until `remaining` is 0). A date holding more than 3 of the event's rows is taken for another edition or day of the meet (an event id and title reused across years) and is never moved unasked: the dry run lists it under `crowded`, and the run refuses until it is listed in `keepDates` (left alone) or `moveDates`.

National rankings and the club list are served from their last build even while a change to them is pending: computing them live is more than one query may read. A ranking class or club list with no view yet is answered live only when it fits one page, and otherwise fails with "being built" until the refresh builds it.

## Writes that skip the ingest mutations

Anything that changes data another way leaves no hints and rewrites no histories or summaries. That includes:

- editing or deleting rows in the Convex dashboard;
- `npx convex import`, such as a bulk load from Postgres;
- a one-off `internalMutation` that patches source tables directly.

After one of those, bring the derived data back in step (add `--prod` for production):

```sh
npx convex run migrations:backfillNameKeys    # fills lifting_results.nameKey, then starts views:rebuildAll
```

`backfillNameKeys` also rekeys every row after a change to `normalizeName`. `views:rebuildAll` rebuilds the histories and their summaries, views, search directory and shards in stages; it runs on its own after `backfillNameKeys`, or can be started directly. It also deletes the history and summary documents of names left with no results, deletes every view it did not rebuild and no later write names (a deleted meet, ranking class or WSO, an old adaptive season), and clears every pending change written before it started. A build that fails is logged and left pending for a targeted refresh instead of stopping the rebuild (or starting another), and the hourly `views-refresh` job alerts until a refresh builds it. While it runs, a refresh checks on it every minute and, if a stage stopped for 15 minutes, resumes it where that stage started. To rebuild only the search shards from the current directory, run `npx convex run views:buildSearchShards`. Name search (`results:search`) ignores case, Unicode composition, how wide a run of spaces is (`Nick Eudy` finds `Nick  Eudy`) and which apostrophe a name uses (`O'Neal` finds `O’Neal`), and suggests one spelling per athlete (`normalizeName`); the shards are built with the same folding (`lib/directory.ts`, `foldForShards`). The shard size table's key carries the fold's version (`SEARCH_SHARD_SIZES_VIEW`; bump it with the fold): after a deploy that changes it, search reads the whole directory until the hourly `views-refresh` job (or `views:buildSearchShards`) builds the shards under the new fold.

A view is fresh while no change it reads is pending, whatever the code that built it. So a deploy that changes what a view holds (a field added to `/data/records`, say) serves the old answer until the view is rebuilt: rebuild the views built by the function you changed, such as `npx convex run views:buildReferenceTables` (records, standards, qualifying totals, international rankings, adaptive records) or `npx convex run views:buildWso` (WSO records), or start `views:rebuildAll`.

Check the result with `npx convex run parity:run`. It compares every fast path (views, histories, summaries, search shards) with a live computation from the raw tables and should report 0 mismatches. `migrations:countPage` counts a table a page at a time, for checking a load against its source.

## Saved sessions

Saved sessions (`convex/users.ts`) are user data, not competition data: they feed no view, history, summary or search shard, so a write to them needs nothing rebuilt. The app's outbox sends each write with its install id and revision (`device`, `rev`), and the server ignores a write that arrives after a newer one from the same install, such as a save that lands after the client timed out and then unsaved. It remembers the last revision each install applied to a session (`saved_session_revisions`, kept after a delete as the session's tombstone) and to a reset of a meet or of everything (`saved_session_resets`). A write from another install, or from an app too old to send a revision, applies as it arrives. Each ordered write deletes up to 32 of the user's records older than 7 days from each table; they only have to outlive a delayed request.

When a user deletes their account in Clerk, Clerk's `user.deleted` webhook (`POST /clerk/webhook` on the deployment's `.convex.site` host, Svix-signed with `CLERK_WEBHOOK_SECRET`) runs `users:deleteUserData`, which deletes their saved sessions, preferences, write-order records, stored entitlement, MeetCal-issued tokens and meet submissions (with their files), and keeps only their id in `deleted_users`, so a request still carrying a valid token for the account is refused (403) rather than storing its data again.

## Meet submissions

Signed-in users can send the schedule and start lists of a meet MeetCal does not cover yet: from the app's Settings ("Submit a Meet") and from meetcal.app/submit-meet (`convex/meetSubmissions.ts`). The client asks `meetSubmissions:generateUploadUrl` for a one-time upload URL per file, POSTs the file to it, and sends the meet's name, dates and the files' storage ids to `meetSubmissions:submit`. The server checks the files in storage (at most 10, 20 MB each, a PDF, image, spreadsheet or Word document by name) and allows 5 submissions and 50 upload URLs per user a day. It stores the submission (`meet_submissions`, `meet_submission_files`) and then emails it in the background (`meetSubmissions:email`) to `MEET_SUBMISSION_EMAIL`, with Reply-To set to the email address the client reported for the user. OneSignal email has no attachments, so the email links to each file. A failed send is retried after 1, 5 and 30 minutes, then throws, so it reaches the logs and Sentry; resend one by hand with `npx convex run meetSubmissions:email '{"submissionId":"…","attempt":0}'`. Without `MEET_SUBMISSION_EMAIL` the submission is stored and only logged. Set it on dev and prod:

```sh
npx convex env set MEET_SUBMISSION_EMAIL maddisen@meetcal.app
```

The daily `meet-submissions-cleanup` job deletes submissions and their files 30 days after they were sent (the email's links stop working then). It also deletes any stored file older than a day that no submission lists: an upload abandoned before submitting. Every file in the deployment's storage is a submission's; a new use of file storage needs that sweep changed first.

## Premium data

The queries that answer what the app's paywall gates (records, standards, rankings, club and WSO data, athlete results and bests, meet results, the offline meet package, and `results:search` when asked for results) are listed in `PREMIUM_FUNCTIONS` (`convex/lib/access.ts`). Each takes a `pass` argument and checks it before anything else (`premiumRead`). Schedules, start lists, meet lists and name suggestions stay public, and so does Weightlifting Wrapped: `results:wrapped` scores one athlete's calendar year on the server (`convex/lib/wrapped.ts`) and answers only the stats, never the results behind them, so the app, website and CLI show it to everyone. Those stats include the year's best snatch, clean & jerk and total, for any year: free yearly bests are part of free Wrapped by decision (October 2026), while the premium queries keep the per-meet results, histories and rankings. A name-contains search that matches `WRAPPED_FALLBACK_NAMES` or more athletes answers `narrow` before reading any history, which keeps the public query cheap.

Two premium answers are actions rather than queries. `results:leaderboard` ranks every athlete in a date range by their best total, snatch, clean & jerk, Sinclair or Q-points (`convex/lib/leaderboard.ts`, the CLI's own rules moved to the server: its source-error guard is the CLI's, which differs from `lib/plausible.ts`'s, see the module's comment). It pages through `lifting_results` by `by_date` a month at a time, 2,000 rows per internal query (`results:leaderboardPage`), eight months side by side, so no single query reaches Convex's read limits, and ranks them in the action, holding about `limit` athletes (`pruneBests`); it answers only the ranked rows, never the results behind them. A page takes only its month and cursor, not the metric, filters or pass, and answers compact rows (about 300 KB for 2,000), so Convex caches each page once for every caller and leaderboard: a call reads about 28,000 results per year of its range (14 pages a year, up to about 140,000 for five years), but a past month's pages come from the query cache until its results change, so in practice only the current month (and any month a sync just wrote to) is read from the database. The range must be under five years and `limit` 1 to 500 (default 50); Sinclair and Q-points need a gender. Actions are not cached and cannot use `premiumQuery`, so it reads the pass row through `accessPass:passes` and applies the same gate (`checkPass`). It is listed in `PREMIUM_ACTIONS`, apart from `PREMIUM_FUNCTIONS` (queries only, which the app and website attach the pass to by name); the CLI attaches the pass to it explicitly. Unlike the queries, it refuses a call without a current pass even in `log` mode (`ENFORCED_FROM_THE_START`): no shipped client calls it without one, and an action's own work is never cached (each call parses and ranks its whole range, and reads whatever pages the query cache does not hold), so an open action would be a cost anyone could run up. There is no query that exports every result in a range: `results:page`, which did, is gone (October 2026), so CLI 2.4.0 and earlier, which read it for `leaderboard` and `results`, fail those two commands; the current CLI ranks with `results:leaderboard` and has no `results` command.

The other, `results:wsoElite`, is a WSO's elite lists (`convex/lib/elite.ts`): the top 20 women and men Overall, Youth (17 and under), Junior (18-20), Senior (21-34) and Masters (35 and over), each list scored by % of A standard, Q-points, Q-masters (Q-points times Huebner's 2025 age factor) or Sinclair. Results carry no WSO, so its members come from registrations (`athletes`): an athlete is the WSO's when their latest registration (by meet start date) that names a WSO names this one, and their birth year is the year of their latest registration that gives an age, less that weightlifting age. It answers `lists` (each list by the method asked for, which the CLI prints) and `rankings` (every list by every method it offers, so the website's score pickers switch without asking again). So the lists only hold athletes who entered a meet whose entries MeetCal syncs (`entry_targets`); adding targets widens them. The action pages the WSO's registrations (`results:eliteRegistrations`, 2,000 a page), looks members up 100 at a time (`results:eliteMembers`), reads their histories 50 names at a time within the range (`results:eliteResults`, USAW rows only, adaptive included) and the A standards (`results:eliteStandards`), eight reads side by side, and ranks in memory; it answers only the ranked rows. It is gated like `results:leaderboard` (`PREMIUM_ACTIONS`, `ENFORCED_FROM_THE_START`); the website and the CLI send it the pass (`SUBSCRIPTION_ACTIONS` in `web/src/utils/api.rs`, `PREMIUM_ACTIONS` in `cli/src/utils/access.rs`).

The pass is one random value shared by every subscriber (`convex/accessPass.ts`). Because every subscriber sends the same arguments and no premium query reads who is calling, Convex caches each premium answer once for everyone, as it does for public queries. `accessPass:pass` gives it to a caller with an active entitlement, signed in with Clerk or a MeetCal-issued token: `{ pass, rotatesAt }`, 401 signed out, 403 without the entitlement. The daily `rotate-access-pass` job (09:00 UTC) makes a new pass current and keeps the one it replaced, so a client's pass works for at least a day. A rotation clears every premium query's cache once, since each reads the pass row. A subscription that lapses stops getting new passes once its `entitlements` row says so (normally RevenueCat's expiry webhook); a pass already handed out keeps working until the rotation after next, so access ends at most about two days after. There is no pass until the first rotation: run `npx convex run accessPass:rotate` once after deploying. To shut out a pass that leaked, run it again (twice to shut out the previous one too).

`PREMIUM_MODE` decides what the gate does with a read that has no current pass:

- `log` (now): answers it, and each run that misses Convex's query cache logs `[premium] <function> without a pass` or `with a stale pass`. The share of those shows how many reads still come from app versions that send no pass.
- `enforce`: refuses it, 401 without a pass and 403 with a stale one. The app, website, CLI and Siri then fetch a new pass and retry once. Switch to it only once nearly every active subscriber runs an app that sends the pass (Siri's included: it needs the build with the Siri token, a native change, and the app opened once after it for the token to be stored), and once:
  - `npx convex run entitlements:backfillKnownUsers` has run on prod (it asks RevenueCat about every user Convex knows from saved sessions, preferences and MeetCal-issued tokens, 50 at a time, scheduling itself until done, skipping users already asked in the run, and stopping if a whole batch fails; `entitlements:backfillUsers` takes a list of any length, e.g. from RevenueCat's customer export), so lifetime subscribers who never opened a pass-sending app already have their entitlement;
  - TestFlight testers and App Review, who buy with sandbox receipts prod does not count, have a reviewer account or another way in.

  Already in place: the app waits (briefly) for Clerk on a cold start while the SecureStore auth hint says someone is signed in (`useServerDataAccess`); a client whose pass is refused fetches a new one and retries, and asks `entitlements:refresh` when the server knows of no subscription; and `parity:run` reads premium queries with the current pass (`accessPass:currentPass`).

A caller has an active entitlement when their `entitlements` row (`convex/entitlements.ts`) is active and not past `expiresAt`. The row is RevenueCat's answer for the Clerk user id (the app user id RevenueCat knows them by), fetched from RevenueCat's REST API whenever:

- RevenueCat's webhook (`POST /revenuecat/webhook` on the `.convex.site` host) reports any event for the user. Configure it in RevenueCat with every event type and an Authorization header value, and set that value as `REVENUECAT_WEBHOOK_AUTH`. A failure answers 500, so RevenueCat retries.
- The app, website or CLI calls `entitlements:refresh` because `accessPass:pass` answered 403 for a user RevenueCat says subscribes (at most once a minute per user on the server). This covers a purchase before its webhook lands, and lifetime purchases, which never send a renewal.
- `npx convex run entitlements:sync '{"userId":"user_…"}'`, for support.

The REST calls need `REVENUECAT_SECRET_API_KEY` (a v1 secret key from RevenueCat's API keys page). A sandbox purchase (TestFlight, a Play license tester, a test card) counts only where `REVENUECAT_COUNT_SANDBOX` is `true`: set it on dev, never on prod. RevenueCat names only the longest-lasting purchase for the entitlement, so a sandbox lifetime purchase hides a promotional grant: when the named purchase is a sandbox one, an unexpired, non-sandbox `rc_promo_Subscriptions_*` grant listed under `subscriptions` counts instead (to give someone whose purchase was a sandbox one access on prod, grant them the entitlement as a promotional in RevenueCat). An answer RevenueCat gave before the stored one is dropped, so events handled out of order cannot bring back a stale state. When RevenueCat was last asked, and the refresh throttle, are kept in `entitlement_syncs`, apart from the row `accessPass:pass` reads.

The app fetches the pass as soon as it believes the user subscribes and attaches it to premium reads (`src/hooks/useServerDataAccess.ts`, `src/lib/api/premium-queries.ts`); the website fetches it before its first premium read (`web/src/utils/api.rs`). Neither sends the user's token on any data read, and neither do the CLI and Siri (below).

Clients that cannot hold a Clerk session (the CLI, Siri's App Intents) get the pass with MeetCal-issued tokens (`convex/apiTokens.ts`): `apiTokens:issue` gives a signed-in Clerk user a 90-day ES256 JWT for this deployment, which Convex accepts as a second auth provider (`convex/auth.config.ts`; issuer `CONVEX_SITE_URL`, keys at `/.well-known/jwks.json`). One is honoured only while its `api_tokens` row exists: `apiTokens:revoke` and account deletion delete it. These tokens can get the pass and nothing else of the user's: saved sessions and preferences refuse them. Set the signing key once per deployment:

```sh
npx convex env set MEETCAL_TOKEN_SIGNING_KEY "$(mise exec -- bun scripts/generate-token-signing-key.ts)"
```

The CLI gets its token by device-code login (`convex/deviceLogin.ts`), so it signs in without a browser on its machine (over SSH, on a server, in an agent's sandbox):

1. `meetcal login` calls `deviceLogin:start` and shows a short user code with a link to `https://meetcal.app/link?code=…` (`DEVICE_LOGIN_URL` overrides the page on dev) and a QR code of it.
2. The user opens the link on any device, signs in with Clerk, sees which device is asking (`deviceLogin:describe`) and approves (`deviceLogin:approve`) or denies it.
3. The CLI polls `deviceLogin:poll` every 5 seconds with its secret device code and, once approved, gets a 90-day token, once.

A code lasts 10 minutes. Only the device code's hash is stored. Approving needs a Clerk session, not a MeetCal-issued token. The approver can still deny the login until the CLI collects its token; a poll after the token went out answers `collected`, so a CLI whose answer was lost is told so. `start` refuses (503) when the deployment cannot sign tokens, before anyone approves. To undo a login approved by mistake, `apiTokens:revokeAllCli` (the Sign out all CLI logins button on meetcal.app/link) ends every CLI token of the signed-in user and turns down logins they approved that the CLI has not collected yet.

Siri's App Intents (`plugins/ios-app-intents/`, compiled into the iOS app target) get their token from the app (`src/lib/siri-token.ts`, run from the root by `src/hooks/useSiriToken.ts`, iOS only):

- While a subscriber is signed in (Clerk loaded, `isSubscribed` true), the app makes sure one is stored: it calls `apiTokens:issue` with `{ client: "siri" }` and the user's Clerk token when none is stored, the stored one is another user's, or it expires within 14 days, then ends the token it replaced. It checks on launch, on a change of user or subscription, and on every return to the foreground. A failed issue is tried again an hour later (for that user: another user signing in does not wait).
- It stores `{ token, tokenId, expiresAt, userId }` as JSON in the keychain with expo-secure-store (service `meetcal.siri`, key `siri_api_token`, `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`, so Siri can read it on a locked phone once it has been unlocked since starting, and a backup restored to another phone does not carry it). expo-secure-store saves that item under the service `meetcal.siri:no-auth` with the key, as data, for its account, and `SiriToken` in `MeetCalAPI.swift` reads exactly that; the intents run in the app's process, so it is the app's own keychain item. A test (`src/lib/siri-token.test.ts`) keeps the names equal and fails if an expo-secure-store upgrade moves the item.
- When the user signs out, or another user signs in, the app ends the stored token with the token itself (`apiTokens:revoke` called with a MeetCal-issued token ends that token, so no Clerk session is needed after it is gone) and deletes it. Offline, the revoke fails and the token, held by nobody, runs out on its own. A user who stops subscribing keeps theirs: it gets no pass while the server sees no subscription.
- Siri reads the token on each premium query (`premiumFunctions` in `MeetCalAPI.swift`, kept equal to `PREMIUM_FUNCTIONS` by `convex-tests/access.test.ts`), gets the pass from `accessPass:pass` with it (asking `entitlements:refresh` once on a 403, as the app does), holds the pass in memory and in the app's `UserDefaults` until its `rotatesAt` (at least 5 minutes), adds it as `pass`, and on a 401 or 403 fetches a new one and retries once. When `accessPass:pass` answers 401 the server no longer accepts the token (revoked, evicted by `MAX_API_TOKENS_PER_USER`, or a replaced signing key): Siri deletes it, and the app issues a new one the next time it opens. Convex answers any token it cannot verify with HTTP 401 (`InvalidAuthHeader`, checked on dev), never 403, so this covers a replaced key too; the cost is that a moment when this deployment's JWKS cannot be read would also make Siri drop a token that was fine, until the app is next opened. Without a token or a pass it sends the query without one. The token never goes on a data query. `PremiumGate` (the App Group entitlement hint) still decides what the intents show.

Replacing it ends every MeetCal-issued token. Account deletion also deletes the user's entitlement records and tokens.

## Meet time zones and dates

The meet scrapers take a meet's time zone from its state, or its city in a state that spans two zones (`convex/scrapers/lib/states.ts`). A meet abroad, or in a US territory, takes the zone of its country when the country keeps one clock (`convex/scrapers/lib/countries.ts`; Spain, Portugal, New Zealand and Ecuador except their outlying islands). A meet in a country with several zones (Canada, Mexico, Australia, Brazil, ...), or a state or country they do not know, keeps the zone it has, or gets a blank one if new, and the run reports it. To set a zone by hand, use `npx convex run ingest:setMeetTimeZone '{"name":"…","timeZone":"America/Vancouver"}'`. It accepts any IANA zone, spelled as the tz database spells it (`isMeetTimeZone` in `convex/lib/validation.ts`), and refuses abbreviations ("EST"), offsets ("+09:00") and other casings, which some clients cannot read. Session times are meet-local wall-clock times everywhere: the app labels them with the zone at the meet ("EDT" in the US, "GMT+9" where the zone has no lettered name) and converts them in that zone for reminders, calendar events and the next-session card; the website and CLI print the zone's name. This locks the zone so the nightly syncs leave it alone. Pass `"locked":false` to hand it back to them. A meet with a blank zone is completed once its last day has ended everywhere on Earth (UTC-12). `npx convex run scrapers/queries:meetDataProblems` lists blank zones and names that are not IANA zones, zones the state, city or country now place elsewhere, and dates that are not padded `YYYY-MM-DD`. `npx convex run migrations:padMeetDates` pads the unpadded dates.

## Scheduled jobs and alerts

`convex/cronJobs.ts` lists every job and its UTC schedule. Each run goes through `cronJobs:run`, which records it in `cron_status`. It emails `ALERT_EMAIL` (through OneSignal) when a job fails and again when it recovers. The hourly `cron-watchdog` emails when a job misses its run or never finishes. The hourly `views-refresh` job runs a refresh even when none is scheduled, so views catch up after a refresh that failed or was lost. It fails, and so emails, when a write has waited over two hours for its views, or when the full rebuild keeps stopping. `urlwatch` emails page changes to `URLWATCH_EMAIL`, including the PDFs USA Weightlifting's qualifying totals pages link to: the qualifying totals are loaded by hand (`ingest:replaceQualifyingTotalSet`), so a new or replaced PDF there is the cue to load it, and next season's page needs adding to `WATCHED_PAGES` once USAW publishes it. Each set is named for its season (`2027 Series`, `2027 Finals`, `2027 Nationals`, with an `(Adaptive)` twin for USAW's adaptive column); the app opens on the newest `YYYY Nationals`. Rename a set with `ingest:renameQualifyingTotalSet` and delete one that no longer qualifies anyone with `ingest:deleteQualifyingTotalSet`. Set both variables on prod only.

`wso-records` reads each Google Sheet tab by gid or by name, checked first against the sheet's visible tabs (its `htmlview` page): a tab the WSO hid, renamed or deleted fails that WSO rather than Google serving a hidden tab's stale records or its first tab instead. Google answers a burst of sheet requests with 429, so the job fetches a WSO's tabs four at a time and tries a throttled (429), server-failed (5xx) or timed-out request again after 2, 4 and 8 seconds (`fetchSheetText`); a 404 fails at once. A record date in the future fails its source too (`correctRecordDate` in `convex/scrapers/parse/holder.ts`); a cell a source wrote with the wrong year goes in that file's `DATE_CORRECTIONS`. The WSO records answers offer only the WSOs the job scrapes (`MAINTAINED_WSOS` in `convex/lib/wsoSources.ts`, kept in step with `WSO_SOURCES` by a test); `npx convex run migrations:deleteUnmaintainedWsoRecords` deletes the rows of any other.

`iwf-world-records` reads IWF's own world-records pages (`convex/scrapers/parse/iwfSite.ts`) through [Browserless](https://www.browserless.io)'s `/unblock` API, because iwf.sport answers plain requests with a Cloudflare bot challenge. It does this only where `BROWSERLESS_TOKEN` is set, and it sends the token in the Authorization header, never in a URL. Without the token, or when any of IWF's six pages fails, it uses Wikipedia's three record lists instead, whole (the two sources are never mixed). The two write holders differently ("RI Song Gum", "Aichi-Nagoya" against "Ri Song-gum", "Asian Games, Nagoya, Japan"), so a day that falls back keeps the stored holder of every lift whose record has not changed. A fallback logs a warning, except when Browserless refuses for the plan (402; a 429 still there after a second try; a 401 or 403 about units, quota or billing; the free tier has 1,000 units a month). That one is expected, so it is only logged at info level. A refused token (a 401 or 403 that is not about the plan) is different: the job still stores Wikipedia's records, then fails naming `browserless`, so the cron alert emails it and Convex's exception reporting sends it to Sentry. No other fallback throws, so none of them reaches Sentry. A throttled, server-failed or timed-out Wikipedia request is tried again after 2, 4 and 8 seconds. If it still fails, the run is skipped with a warning in the logs and the stored records are kept, so a passing Wikipedia outage does not email. A 404 or a table it cannot read still fails the run. Set the token on prod only:

```sh
npx convex env set BROWSERLESS_TOKEN <token> --prod
```

A job that reads many sources (a WSO each in `wso-records`, a meet each in `results-sport80`, a target each in `entries`, a tab or PDF each in `umwf-records` and `intl-rankings`) stores what it could read, then fails naming the sources that failed (`sourcesFailed` in `convex/lib/cronAlerts.ts`). `cron_status.failedSources` keeps that list, and a source that starts failing while the job is already failing emails again, so a second outage is not hidden behind the first.

The watchdog's own runs are recorded in `cron_status` under `cron-watchdog`, and every job's run checks that it ran: one that misses its run or never finishes is emailed like any job. After a run that checked every job and sent every alert, the watchdog GETs `HEARTBEAT_URL`, a dead man's switch such as a [Healthchecks.io](https://healthchecks.io) check with an hourly period. The monitor alerts on its own when the pings stop, which catches what no email from the backend can: the crons stopped, the watchdog keeps failing, or OneSignal email broke. Unset (the dev deployment), nothing is pinged. Set it on prod only:

```sh
npx convex env set HEARTBEAT_URL https://hc-ping.com/<uuid> --prod
```

### When a sync refuses to delete

The syncs that delete what a source no longer lists refuse to delete more than a share of it at once, because a source that partly broke looks the same as data that went away. The run fails and the email says which limit was hit and the command to run once you have checked the source by hand:

- `wso-records` refuses to delete more than a quarter of a WSO's classes (at least 20 always allowed), or to clear as many of its stored lifts (a cell the parser could not read now fails the WSO instead of clearing the record). Override: `npx convex run scrapers/wsoRecords:run '{"only":["<WSO>"],"allowShrink":true}'`.
- `results-sport80` deletes an event's stored results its Sport80 table no longer has (a corrected name, a withdrawn result, the meet's old title), only for a meet whose every row was read and whose table has the rows its `total` reports with no row repeated across pages (a table reporting no `total`, or repeating a row, is stored but not pruned, and fails the run), and refuses to drop more than a tenth of an event's athletes (at least 5 always allowed; rows only retitled do not count). It also refuses to empty a column (a lift, the total, the body weight) on over half of the stored results it updates, which is what a column Sport80 renamed looks like. Override: `npx convex run scrapers/sport80:run '{"only":["<event id>"],"allowShrink":true}'`. The nightly run reads only the 30 newest events, so it stops retrying (and naming) an event once 30 newer ones exist; `only` reaches any event of this year or last, and fails on an id the event index does not have. A meet with over a fifth of its rows unreadable fails the run.
- `records`, `umwf-records` and `usamw-national-records` (`ingest.upsertRecords`) refuse to clear more than a quarter of the matched records' stored lifts (at least 20 always allowed). Each then deletes the classes its source no longer lists, such as the classes a class change retired (`ingest.pruneRecords`): the whole record type for `records` and `usamw-national-records`, only the age groups whose tab was read for `umwf-records`. `records` prunes nothing, and fails, when the PDF has an age group the parser does not know. The prune refuses to delete more than a quarter of the classes in its scope (at least 20 always allowed), or every class of an age group and gender (a relabelled age group looks like that; a class change does not), and is checked before anything is written, so a refused run stores nothing. `'{"dryRun":true}'` lists what it would delete and why it would refuse. Override: `npx convex run scrapers/umwf:run '{"allowShrink":true}'` (or `scrapers/records:run`, `scrapers/usamw:run`).
- `standards` stores the standards in force today in Colorado Springs (a PDF listing the classes before and after a class change has a dated heading on each half) and deletes the classes the PDF no longer lists (`ingest.pruneStandards`), with the same limits, checked the same way. Override: `npx convex run scrapers/standards:run '{"allowShrink":true}'`.
- `intl-rankings` refuses to prune more than a quarter of the stored groups (at least 2 always allowed). Override: `npx convex run scrapers/intlRankings:run '{"allowShrink":true}'`.

Add `--prod` for production. The `entries` job skips a target whose meet is completed before downloading its list, and removes the target 14 days after the meet ended. Once any athlete of a meet has a session (its start list is published), it adds no new athletes to that meet, only updates the ones there. Sport80's entries list carries no WSO, so the sync stores each entrant's WSO from their registration naming one at the latest-starting meet (`scrapers/queries:memberWsos`; start lists loaded by hand carry WSOs), and never clears a stored one. An entrant already placed in a session gets only a WSO it lacks. An athlete has a session when they have both a session number and a platform (`lib/roster.ts`, `hasSession`). Until then, an entrant the whole list no longer has (withdrawn) is deleted, up to a quarter of the meet's entrants (and always 5); past that the run fails naming them, and `'{"only":["<label>"],"allowShrink":true}'` lets it through after checking. A member Sport80 renamed, or one stored under a nine-digit id the old scraper minted, is updated in place rather than added twice. Sport80's empty-table placeholder (`undefined undefined`) and membership numbers that are neither digits nor a `noid:` placeholder are not stored.

`ingest:replaceMeetAthletes` (a start list loaded by hand) refuses a row with only one of session number and platform, and refuses a list `rosterProblems` finds wrong (ages outside 5-100 or one age for much of the roster, `+` classes dropped, a weight class only the other gender has, a gender that is neither, a placeholder entrant), naming the rows, unless `'{"allowUnchecked":true}'` is passed. A blank membership number is stored as the `noid:` placeholder.

`npx convex run migrations:cleanupRosterRows` lists the roster rows old entries scrapers left: placeholder entrants, meets named after a cookie banner or a CSV line, unscheduled copies of start-list athletes, and one-off ids beside the athlete's real number. With `'{"dryRun":false}'` it deletes them through the write path.
